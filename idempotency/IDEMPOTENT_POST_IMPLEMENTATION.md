# Idempotent POST APIs — Spring Boot + Oracle Implementation Guide

> Independent learning/demo material. The examples are illustrative and contain no employer or client code, data, credentials, or confidential design.

This guide turns the idempotency section in the repository README into an implementation blueprint for a payment-style API. It uses **Spring Boot, JdbcTemplate for the idempotency record, Oracle SQL, and a Hibernate SessionFactory-based DAO** for the business write.

The central guarantee is:

> For one authenticated merchant, one operation, and one idempotency key, the server creates at most one committed business result during the key's retention period.

Idempotency does not mean that the HTTP request is executed only once. The server may receive the request many times; it ensures retries resolve to the same committed result.

## 1. The failure this solves

Imagine a client sends:

~~~http
POST /api/v1/payments
Idempotency-Key: 8f2c...random-client-key
Content-Type: application/json

{
  "beneficiaryId": "BEN-101",
  "amount": "250.00",
  "currency": "INR"
}
~~~

The server commits the payment, but the network drops before the client receives the response. The client cannot know whether the payment succeeded.

Without idempotency, retrying the POST can create a second payment.

~~~text
Client                 API                    Database
  |                     |                         |
  | POST + key K        |                         |
  |-------------------->| create payment          |
  |                     |------------------------>|
  |                     |       COMMIT            |
  |                     |<------------------------|
  |       response lost |                         |
  X                     |                         |
  |                     |                         |
  | retry same key K    |                         |
  |-------------------->| find completed result   |
  |<--------------------| return saved response   |
~~~

The key is generated by the client and reused for retries of the **same logical operation**. A new payment must use a new key.

## 2. Define the contract before writing code

| Situation | Expected behavior |
|---|---|
| First request with a new key | Validate, create one payment, persist the response, return success |
| Same key + same normalized request | Return the previously stored response; do not create another payment |
| Same key + different request | Return 409 Conflict; never silently reuse the old result |
| Two concurrent requests with the same key | Database uniqueness allows only one transaction to create the result |
| First transaction rolls back | Its idempotency row and payment both roll back; a retry can safely attempt the operation |
| Client times out after commit | Retry with the same key and payload; replay the committed result |

### Scope the key safely

Do not make the key globally unique by itself. Scope it by:

- authenticated merchant/tenant;
- operation name, such as CREATE_PAYMENT_V1;
- client-supplied idempotency key.

Derive the merchant identity from the authenticated principal. Do not trust a merchant ID supplied only in the request body or an arbitrary header. This prevents one merchant from replaying or inspecting another merchant's result.

## 3. Oracle table and uniqueness constraint

The unique constraint is the concurrency control. A Java SELECT followed by an INSERT is not safe: two requests can both observe that the key is absent.

~~~sql
CREATE TABLE API_IDEMPOTENCY (
    MERCHANT_ID          VARCHAR2(64)  NOT NULL,
    OPERATION_NAME       VARCHAR2(60)  NOT NULL,
    IDEMPOTENCY_KEY      VARCHAR2(128) NOT NULL,
    REQUEST_HASH         CHAR(64)      NOT NULL,
    PROCESSING_STATUS    VARCHAR2(16)  NOT NULL,
    RESPONSE_STATUS      NUMBER(3),
    RESPONSE_BODY        CLOB,
    CREATED_AT           TIMESTAMP     DEFAULT SYSTIMESTAMP NOT NULL,
    COMPLETED_AT         TIMESTAMP,

    CONSTRAINT PK_API_IDEMPOTENCY
        PRIMARY KEY (MERCHANT_ID, OPERATION_NAME, IDEMPOTENCY_KEY),

    CONSTRAINT CK_API_IDEMP_STATUS
        CHECK (PROCESSING_STATUS IN ('PROCESSING', 'COMPLETED')),

    CONSTRAINT CK_API_IDEMP_DONE
        CHECK (
            PROCESSING_STATUS <> 'COMPLETED'
            OR (
                RESPONSE_STATUS IS NOT NULL
                AND RESPONSE_BODY IS NOT NULL
                AND COMPLETED_AT IS NOT NULL
            )
        )
);
~~~

Why the composite primary key matters:

- The database, not application memory, coordinates concurrent requests across multiple application instances.
- A restart or horizontal scale-out does not lose the idempotency decision.
- The same key can be used by different merchants or different operations without collisions.

The response body should be the stable API response DTO, not a JPA/Hibernate entity. Keep it small and avoid storing secrets or unnecessary personal data.

## 4. Calculate a request fingerprint

The idempotency key alone is insufficient. Store a SHA-256 fingerprint of the **normalized business request** so that reusing a key with a different amount or beneficiary is detected.

Normalize equivalent values before hashing. For example, 250.0 and 250.00 should represent the same amount if the API contract treats them as equivalent.

~~~java
@JsonPropertyOrder({
    "merchantId", "beneficiaryId", "currency", "amount"
})
public record CanonicalPaymentRequest(
        String merchantId,
        String beneficiaryId,
        String currency,
        String amount) {
}
~~~

~~~java
public String createRequestHash(
        String merchantId,
        CreatePaymentRequest request,
        ObjectMapper objectMapper) {

    try {
        CanonicalPaymentRequest canonical =
                new CanonicalPaymentRequest(
                        merchantId,
                        request.beneficiaryId().trim(),
                        request.currency().toUpperCase(Locale.ROOT),
                        request.amount().stripTrailingZeros().toPlainString());

        String canonicalJson = objectMapper.writeValueAsString(canonical);

        byte[] digest = MessageDigest.getInstance("SHA-256")
                .digest(canonicalJson.getBytes(StandardCharsets.UTF_8));

        return HexFormat.of().formatHex(digest);
    } catch (JsonProcessingException | NoSuchAlgorithmException ex) {
        throw new IllegalStateException(
                "Could not create payment request fingerprint", ex);
    }
}
~~~

The canonical DTO must include every field that changes the business meaning of the operation. Do not include volatile transport fields such as trace IDs, request timestamps, or client retry counters. If the request contains nested collections, sort them only when order is not meaningful in the business contract.

## 5. Transaction design: commit the payment and replay record together

For a short, database-only operation, use **one database transaction**:

1. Insert an idempotency row as PROCESSING.
2. Create the payment using the Hibernate DAO.
3. Serialize the stable response DTO.
4. Update the idempotency row to COMPLETED with the response.
5. Commit both the payment and idempotency row together.

If any step fails, both writes roll back. A committed PROCESSING row should not normally be visible in this design because the row is changed to COMPLETED before the same transaction commits.

### Transactional writer

The following is an illustrative service. Supporting DTOs, entity mappings, exception advice, and configuration are intentionally omitted; adapt names to the application.

~~~java
@Service
public class NewPaymentTransaction {

    private static final String OPERATION = "CREATE_PAYMENT_V1";

    private static final String INSERT_IDEMPOTENCY = """
        INSERT INTO API_IDEMPOTENCY
        (MERCHANT_ID, OPERATION_NAME, IDEMPOTENCY_KEY,
         REQUEST_HASH, PROCESSING_STATUS)
        VALUES (?, ?, ?, ?, 'PROCESSING')
        """;

    private static final String COMPLETE_IDEMPOTENCY = """
        UPDATE API_IDEMPOTENCY
           SET PROCESSING_STATUS = 'COMPLETED',
               RESPONSE_STATUS = ?,
               RESPONSE_BODY = TO_CLOB(?),
               COMPLETED_AT = SYSTIMESTAMP
         WHERE MERCHANT_ID = ?
           AND OPERATION_NAME = ?
           AND IDEMPOTENCY_KEY = ?
           AND PROCESSING_STATUS = 'PROCESSING'
        """;

    private final JdbcTemplate jdbcTemplate;
    private final PaymentDao paymentDao;
    private final ObjectMapper objectMapper;

    public NewPaymentTransaction(
            JdbcTemplate jdbcTemplate,
            PaymentDao paymentDao,
            ObjectMapper objectMapper) {
        this.jdbcTemplate = jdbcTemplate;
        this.paymentDao = paymentDao;
        this.objectMapper = objectMapper;
    }

    @Transactional
    public PaymentResponse execute(
            String merchantId,
            String idempotencyKey,
            String requestHash,
            CreatePaymentRequest request) {

        try {
            jdbcTemplate.update(
                    INSERT_IDEMPOTENCY,
                    merchantId, OPERATION, idempotencyKey, requestHash);
        } catch (DuplicateKeyException ex) {
            // Let this exception leave the transactional proxy.
            // The transaction is rolled back before the coordinator reads
            // the already-committed record in a separate transaction.
            throw new DuplicateIdempotencyKeyException(ex);
        }

        // This DAO must use the same database transaction.
        Payment payment = paymentDao.create(merchantId, request);
        PaymentResponse response = PaymentResponse.from(payment);

        final String responseJson;
        try {
            responseJson = objectMapper.writeValueAsString(response);
        } catch (JsonProcessingException ex) {
            throw new IllegalStateException(
                    "Could not serialize payment response", ex);
        }

        int updated = jdbcTemplate.update(
                COMPLETE_IDEMPOTENCY,
                201, responseJson,
                merchantId, OPERATION, idempotencyKey);

        if (updated != 1) {
            throw new IllegalStateException(
                    "Idempotency record was not completed");
        }

        return response;
    }
}
~~~

A Hibernate DAO can keep the persistence style explicit:

~~~java
@Repository
public class PaymentDaoImpl implements PaymentDao {

    private final SessionFactory sessionFactory;

    public PaymentDaoImpl(SessionFactory sessionFactory) {
        this.sessionFactory = sessionFactory;
    }

    @Override
    public Payment create(
            String merchantId,
            CreatePaymentRequest request) {

        Payment payment = new Payment(
                merchantId,
                request.beneficiaryId(),
                request.amount(),
                request.currency());

        sessionFactory.getCurrentSession().persist(payment);
        return payment;
    }
}
~~~

**Important transaction configuration:** the JdbcTemplate and SessionFactory must use the same Oracle DataSource and a transaction manager that coordinates both (for native Hibernate, configure the appropriate HibernateTransactionManager with that DataSource). Otherwise the idempotency row and payment could commit independently, breaking the guarantee. Verify this with an integration test; do not assume that two components share a transaction just because both use the same database URL.

## 6. Handle duplicate requests outside the failed transaction

The coordinator itself should not hold a transaction around the writer and replay lookup. The writer and reader are separate Spring beans so their transactional methods are invoked through Spring proxies.

~~~java
@Service
public class IdempotentPaymentCoordinator {

    private static final String OPERATION = "CREATE_PAYMENT_V1";

    private final NewPaymentTransaction writer;
    private final ExistingIdempotencyReader reader;
    private final RequestFingerprint fingerprint;
    private final ObjectMapper objectMapper;

    public IdempotentPaymentCoordinator(
            NewPaymentTransaction writer,
            ExistingIdempotencyReader reader,
            RequestFingerprint fingerprint,
            ObjectMapper objectMapper) {
        this.writer = writer;
        this.reader = reader;
        this.fingerprint = fingerprint;
        this.objectMapper = objectMapper;
    }

    public PaymentResponse create(
            String merchantId,
            String key,
            CreatePaymentRequest request) {

        validateKey(key);
        String requestHash =
                fingerprint.create(merchantId, request);

        try {
            return writer.execute(
                    merchantId, key, requestHash, request);
        } catch (DuplicateIdempotencyKeyException duplicate) {
            StoredIdempotencyResult existing =
                    reader.find(merchantId, OPERATION, key);

            if (!existing.requestHash().equals(requestHash)) {
                throw new IdempotencyPayloadMismatchException();
            }

            if (!"COMPLETED".equals(existing.status())) {
                // Not expected for the single-transaction design.
                // Alert and fail closed; never create a second payment.
                throw new IdempotencyStateException();
            }

            try {
                return objectMapper.readValue(
                        existing.responseBody(), PaymentResponse.class);
            } catch (JsonProcessingException ex) {
                throw new IllegalStateException(
                        "Stored idempotency response is invalid", ex);
            }
        }
    }

    private void validateKey(String key) {
        if (key == null || !key.matches("[A-Za-z0-9._~-]{16,128}")) {
            throw new InvalidIdempotencyKeyException();
        }
    }
}
~~~

The reader uses a separate read-only transaction:

~~~java
@Service
public class ExistingIdempotencyReader {

    private static final String FIND_EXISTING = """
        SELECT REQUEST_HASH, PROCESSING_STATUS, RESPONSE_BODY
          FROM API_IDEMPOTENCY
         WHERE MERCHANT_ID = ?
           AND OPERATION_NAME = ?
           AND IDEMPOTENCY_KEY = ?
        """;

    private final JdbcTemplate jdbcTemplate;

    public ExistingIdempotencyReader(JdbcTemplate jdbcTemplate) {
        this.jdbcTemplate = jdbcTemplate;
    }

    @Transactional(readOnly = true)
    public StoredIdempotencyResult find(
            String merchantId, String operation, String key) {

        return jdbcTemplate.queryForObject(
                FIND_EXISTING,
                (rs, rowNum) -> new StoredIdempotencyResult(
                        rs.getString("REQUEST_HASH"),
                        rs.getString("PROCESSING_STATUS"),
                        rs.getString("RESPONSE_BODY")),
                merchantId, operation, key);
    }
}
~~~

The duplicate-key exception must leave the writer's transactional proxy before the reader runs. Do not catch it and query from inside the same failed transaction. Also avoid calling a transactional method through this.method(); self-invocation bypasses the usual proxy interception.

### Why the unique constraint handles concurrency

If two application instances insert the same scoped key concurrently, Oracle's unique index arbitrates the conflict. The second insert waits for the first transaction's outcome:

- If the first transaction commits, the second insert receives a duplicate-key error; the coordinator reads and replays the completed result.
- If the first transaction rolls back, the second insert can proceed and become the transaction that creates the payment.

This is why the database constraint is essential. A Java-level existence check or an in-memory map cannot provide this guarantee across application instances.

## 7. Controller contract and error mapping

Keep the merchant identity tied to the authenticated principal. The controller should validate the request before it reaches the business operation.

~~~java
@RestController
@RequestMapping("/api/v1/payments")
public class PaymentController {

    private final IdempotentPaymentCoordinator coordinator;
    private final MerchantIdentity merchantIdentity;

    public PaymentController(
            IdempotentPaymentCoordinator coordinator,
            MerchantIdentity merchantIdentity) {
        this.coordinator = coordinator;
        this.merchantIdentity = merchantIdentity;
    }

    @PostMapping
    @ResponseStatus(HttpStatus.CREATED)
    public PaymentResponse create(
            @RequestHeader("Idempotency-Key") String key,
            @Valid @RequestBody CreatePaymentRequest request,
            Principal principal) {

        String merchantId = merchantIdentity.from(principal);
        return coordinator.create(merchantId, key, request);
    }
}
~~~

Map a reused key with a different request to a stable error such as:

~~~json
{
  "code": "IDEMPOTENCY_KEY_REUSED",
  "message": "This idempotency key was already used with a different request."
}
~~~

Return HTTP 409 Conflict for that case. Missing/invalid keys should be rejected as client errors. A transient database lock timeout should be treated as retryable; the client must retry with the **same key and same payload**, never generate a new key just because it did not receive a response.

## 8. Important design boundary: do not call a remote provider inside this transaction

The sample is appropriate for a short operation whose business write and idempotency record live in one database transaction.

Do not hold the database transaction open while calling a payment gateway, sending email, or publishing directly to Kafka. A remote call cannot be rolled back by the Oracle transaction.

~~~text
One Oracle transaction:
  create payment as PENDING
  insert idempotency response/workflow state
  insert OUTBOX event
             |
           COMMIT
             |
             v
Outbox publisher -> provider/worker -> update payment state
             |
             v
Retry with provider-side idempotency key
~~~

The outbox publisher and downstream consumer need their own retry and deduplication strategy. This connects to the transactional-outbox and idempotent-consumer material in the Microservices Engineering Lab.

There is a different architecture called **claim-then-process**, where a PROCESSING row is committed before the business work begins. That design can return an immediate in-progress response, but it requires an owner/lease, timeout recovery, and stale-claim handling. Do not mix its recovery rules with the single-transaction design above.

## 9. Retention and operational safeguards

Choose retention based on the API's documented retry window, client behavior, and any payment-provider requirements. Seven days below is only an example:

~~~sql
DELETE FROM API_IDEMPOTENCY
 WHERE PROCESSING_STATUS = 'COMPLETED'
   AND COMPLETED_AT < SYSTIMESTAMP - INTERVAL '7' DAY;
~~~

- Do not delete keys before the supported retry window ends.
- A key becomes reusable only after its record is removed; document that behavior.
- Run cleanup in bounded batches for large tables and monitor its duration.
- Keep response data minimal; apply access controls and retention rules to any stored personal data.
- Never log authorization tokens or full sensitive request bodies.
- Log a safe key fingerprint or a truncated correlation value, not the raw key.
- Monitor created, replayed, payload-conflict, database-wait, and lookup-failure counts.
- Alert if a committed PROCESSING row appears in this single-transaction design; it indicates a code path or data-integrity problem.

## 10. Integration-test matrix

Use the same database engine as production for the concurrency/constraint tests. H2 can be useful for fast tests, but it is not proof of Oracle locking, CLOB, or constraint behavior.

| Test | Setup | Assertion |
|---|---|---|
| First request | New key and valid request | One payment and one completed idempotency row |
| Same key, same body | Submit the request twice | Same payment ID/response; payment count remains one |
| Same key, changed amount | Reuse key with a different amount | HTTP 409; no second payment |
| Concurrent duplicate | Submit the same key from two threads/clients | One committed payment; both callers resolve to the same result |
| First transaction rolls back | Force failure after payment insert but before idempotency completion | Neither row commits; retry can succeed |
| Different merchant | Same key under another authenticated merchant | Separate scope; no cross-merchant replay |
| Different operation | Same key for another operation name | Separate scope |
| Commit response lost | Commit first request, simulate client timeout, then retry | Stored response is replayed |
| Expired retention | Delete an old completed record according to policy | Reuse behavior matches the documented retention contract |

For the concurrency test, coordinate both requests with a latch/barrier so they really overlap. A sequential test does not prove race safety.

## 11. Common mistakes

- **Check-then-insert:** races under concurrency; use a database unique constraint.
- **Key without tenant scope:** can cause cross-tenant result disclosure.
- **No request fingerprint:** same key with a different amount could receive an unrelated old response.
- **Only storing the key in memory/Redis:** process restart or multi-instance deployment can lose the guarantee unless the durable business transaction is coordinated correctly.
- **Committing the idempotency row separately without recovery:** can leave permanent PROCESSING records.
- **Calling a remote API inside the DB transaction:** the remote side effect cannot be rolled back.
- **Catching the duplicate exception inside the writer and reading immediately:** the transaction may still be active or rollback-only.
- **Using a new key on every retry:** defeats idempotency.
- **Returning the previous result to a different merchant:** creates a data-isolation vulnerability.
- **Deleting records too early:** a late retry can create a duplicate business operation.

## 13. Practical exercises

1. Add a request_hash comparison and return a consistent 409 error for mismatched payloads.
2. Write an Oracle integration test that submits the same key concurrently from two threads.
3. Force a failure after the payment insert and prove that both the payment and idempotency row roll back.
4. Add a bounded cleanup job and test the retention boundary.
5. Extend the flow with an outbox row written in the same transaction; publish it asynchronously and make the consumer idempotent.
